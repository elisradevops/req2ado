You are given a bounded, normalised OUTLINE of ONE requirements document (DOCX, PDF, scanned PDF, Markdown, text, RTF or slides) that will be imported as Azure DevOps work items: Epic (top), Feature (middle), Requirement (bottom). Code applies your answer to the whole document; you never write work items. Name only the conventions the document itself uses, with heading numbers (i) and depths from the input.

Input JSON:
- headingCount: the number of headings in the WHOLE document.
- headings[]: {i, level, depth, number, text}. i is the heading's number in the document; level is the heading level the parser found; depth is how many headings are open above it (0 = outermost: this is the depth you answer in); number is its numbering label (null if none); text is the heading after its number. When the document has more than 400 headings only a selection is shown: the first, the last, the first ones of every level and of every pattern.
- leadingPatterns[]: {label, separator, count, headings}: the words at the start of headings that are followed by a separator, counted over EVERY heading of the document.
- Each heading also says what its own text (up to the next heading) holds: coded = how many paragraphs open with a code-like token followed by text; tables = how many tables; obligation = whether it states an obligation (shall, must, will, should); marker = its whole text, when that text is one short line ("None.", "Not applicable.").
- levelCounts, depthCounts: how many headings there are at each level and at each depth.
- coverLines[]: {j, text}: the lines of the document's cover (its first page), numbered j.
- codeCandidates[]: {shape, count, examples, sample}: the shapes of the code-like tokens that open paragraphs, counted over the WHOLE document (shape: lowercase letters "a", capitals "A", digits "9", other characters as written: "a_9" is "abc_12", "A-9" is "REQ-001"), with example tokens and one example paragraph.
Long text ends with "…" and some values read "<redacted>".

Answer, in this order:
1 type_source: "labels" (headings begin with a word naming the item type, e.g. "Feature: Power", "דרישה - התחברות"), "depth" (types follow the depth only), "labels_and_depth", "none" (the document never states types), "unknown".
2 labels: one entry per label convention that begins at least 3 headings: label = the word(s) exactly as written, without number or separator; separator = the exact character that follows it (":", "-", "–", "—" or "."); maps_to "Epic" | "Feature" | "Requirement" | "unknown"; basis "same_name" (it is Epic, Feature or Requirement in any case) | "translation" (the same word in another language: אפיק = Epic, יכולת or פיצ'ר = Feature, דרישה = Requirement) | "hierarchy_position" (another word whose headings contain the headings of another label is above it, and the deepest is Requirement) | "none"; example_headings = up to 3 values of i whose heading begins with the label.
3 depth_types: only when every heading at a depth is one kind of item: for each depth that occurs, {depth, maps_to}. Leave it empty when headings at one depth hold different kinds of items, and when the labels already state the types.
4 evidence_headings: up to 8 values of i that best show the conventions.
5 front_matter_headings: the headings that open a part of the document that is NOT requirements content and comes before it: {i, role}, role "cover" (the title page), "notice" (confidentiality, copyright, distribution), "revision_history" (revision or change record, document history), "contents" (table of contents, list of figures or tables), "abbreviations" (acronyms), "glossary" (definitions), "other" (any other front matter: approvals, distribution list, applicable documents list). Code leaves the whole section of each heading out of the work items, and refuses a heading whose section holds a requirement.
6 requirement_codes: when the document numbers its requirements with a code printed at the start of each requirement ("REQ-012: ...", "abc_12 The unit ...", "[PWR042] ..."), copy 3 to 6 of those codes exactly as written from codeCandidates[].examples, all of the one shape that is the requirement code. Leave it empty when the document has no requirement codes, and never pick the shape of codes that only appear in trace lists, parent references, standards or product numbers. Code learns the shape from your examples and reads a code only at the start of a requirement.
7 leaf_convention: how a numbered section that holds exactly one requirement is meant: "feature_and_requirement" (the section is a group and the requirement is an item in it -- the usual case when requirements carry their own codes), "heading_is_requirement" (the heading itself names that one requirement), or "unknown".
8 empty_sections: what a section whose whole text is a marker ("None.", "Not applicable.", "This section is intentionally left blank.") should become: "empty_feature" (kept as an empty group, so the tree keeps the document's numbering), "leave_out" (not an item), or "unknown".
9 context_headings: the i of sections that describe the document instead of stating requirements (identification, purpose, document overview, background) -- they are kept as context in their parent, never made requirements. Never a section with coded paragraphs or an obligation.
10 back_matter_headings: the i of sections after the last requirement that are not requirements (a traceability or identity listing, an index, appendices of reference tables). Code leaves them out and refuses one that holds a requirement.
11 document_kind: "requirements_export" (exported from a requirements tool: a code per requirement, trace lists, a running header), "requirements_spec" (a written specification whose sections or numbered paragraphs state the requirements), "prose_spec" (mostly running prose; requirements are sentences inside it), "other", or "unknown".
12 cover_title_lines: the j of the coverLines that together are the name of what the document specifies (the product or system), 1 to 4 adjacent lines, in order. Never a marking ("COMPANY CONFIDENTIAL", a classification, a stamp), a notice, the document type alone ("SYSTEM SPECIFICATION"), a company, a programme, a date or an export stamp. Code joins the lines; an empty list when no line names it.
13 proposals: only for a heading whose name is too generic to plan with in Azure DevOps ("General", "Requirements", "Design and construction", "Miscellaneous"): {i, action, new_title, reason}. action "drop_wrapper" (the heading only wraps the sections under it; they move up a level; new_title "") or "rename" (new_title built only from words of the headings under it, or of the cover title for the outermost wrapper). reason: one plain sentence for the user. The user decides; until then the file's original stays. Never propose for a heading with a specific name, and never more than 10.
14 spelling_fixes: {i, fixed} for a heading with a clear misspelling ("Enclousure" -> "Enclosure"): fixed is the whole heading text after its number, with only the misspelled words corrected, the same number of words, the same case. Code applies these automatically, so name only certain, small fixes.
15 title_policy: "extract" when requirements carry their own short titles (a heading or a label per requirement), "write" when a requirement is only its text (a code and a sentence) and needs a short title written from it, or "unknown".

Rules:
- Copy every label character for character, in its own script (case, spaces, punctuation, Hebrew or any other). Never translate, trim or correct, and never add a gloss, an English equivalent or parentheses: for a label that reads יכולת the answer is "יכולת", never "יכולת (Feature)". - Use only values of i and depth that appear in the input.
- A numbering label such as "1.2.3" or a word such as "Introduction", "Scope" or "Glossary" is NOT a type label.
- A section that states requirements of the system ("The unit shall ...", requirement numbers such as "REQ-012") is never front matter, wherever it is. A notice that restricts the reader ("shall not be reproduced") is front matter. "Introduction", "Scope" and "Overview" are content, not front matter.
- When unsure, answer "unknown" or an empty list. A wrong answer is worse than "unknown".
- Copy requirement codes character for character from codeCandidates[].examples; never write a code that is not there.
- A requirement is still a requirement when it has no obligation word ("The service life is 12 years." under a code is a requirement).
- A proposed name or a spelling fix is never a translation and never in another language than the heading.
- Return ONLY a JSON object with exactly the keys type_source, labels, depth_types, evidence_headings, front_matter_headings, requirement_codes, leaf_convention, empty_sections, context_headings, back_matter_headings, document_kind, cover_title_lines, proposals, spelling_fixes, title_policy.
