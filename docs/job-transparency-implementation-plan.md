# Job transparency: implementation plan (3 phases)

Status: **planned, not started.** Date: 2026-10-05.

Interactive reference (what we are building, today vs proposed, four document types): https://claude.ai/artifact/4myZTuxTM8eBX9XsAq7Yr9

Related docs: [`job-transparency-review.md`](job-transparency-review.md) (current-state findings, IDs T1 to T16) and [`job-transparency-design.md`](job-transparency-design.md). The design doc predates the final direction and centers on token usage and the section list. **Where the two disagree, this plan wins.** The design doc should be revised after Phase 1 (listed under Phase 3, S8).

## 1. What we are building

A running SURVEY job shows what the model is working on and how far along it really is.

| Capability | What the user sees |
|---|---|
| Document map | True counts (sections, headings or rows, words, tables, figures, pages) and an outline with each heading waiting, being worked on, or done |
| Working on | The heading and a short excerpt of its text, plus what the step will do with it |
| Writing | The work item as the model writes it (type, title, running counts), streamed |
| Counted percentage | Built from exact units (words, items, pages, requirements), weighted per stage |
| Comparisons | Conflicts and duplicate matches shown as two texts side by side with a word-level LCS diff |
| Scanned PDFs | Page-by-page reading with the recognised text |

**Fixed decisions:** SURVEY mode only. Read-only (no run controls, no steering, no model-asks-user). Outline plus short excerpt, not full source view. Stream the drafting output. Token usage is secondary (kept out of the main screen; the run summary may show it later). Supported inputs follow the loaders: docx, xlsx/csv, pdf (text and scanned), pptx, rtf, txt, md, images.

**Out of scope:** BASELINE mode, run controls, full source viewer, cost conversion, the 25 quick fixes in `ui-polish-plan.md` (separate effort, but Phase 2 must not conflict with them).

## 2. Principles (each one comes from a fact in the current code)

1. **The stream is a view, not the source of truth.** `_parse_json_object` in `orchestrator_llm_client.py` carries several hard-won tolerances for grammar-constrained decoders (missing braces, unescaped quotes, `json_repair` fallback). Streaming must feed an observer that extracts partial items for display. The final result still comes from the existing parse of the complete text. If the observer fails, results do not change.
2. **Static data and live data travel separately.** Counts, outline and chunk plan are fetched once over REST. Live deltas use new SSE event names. Nothing high-frequency goes into the narration log, which is capped at 50 entries (`NARRATION_LOG_MAX_ENTRIES`, `_NARRATION_LOG_MAX_ENTRIES`).
3. **Additive contracts.** The SSE controller currently sends every non-`narration` message as a `stage` event, so new types need explicit routing. Old browsers ignore unknown event names (the frontend registers `stage` and `narration` listeners only).
4. **Every capability behind its own flag, default off.** Rollback is an environment change.
5. **Privacy by construction.** Excerpts are capped (240 characters), owner-scoped, short-lived, never persisted, never logged.
6. **Concurrency-safe.** `survey_chunk_concurrency` and `survey_branch_concurrency` can exceed 1 (chunks run through `run_chunks_bounded`). The live model has lanes, not a single "current" item.
7. **One owner for the percentage.** Ingestion reports exact units. The orchestrator computes the weighted overall number, where past-run history lives (`eta.service.ts` already fits real job durations).
8. **Honest wording.** "What the model is reading" is inferred from output position, not observed. UI copy says "Working on", and any interpolated cursor is labelled as approximate.

## 3. Target architecture

```
ingestion (parse + /level)                    orchestrator                         browser
-------------------------                     ------------                         -------
loaders -> DocStats ----------+
heading/table/section plan ---+--> Redis  job-events:{id}:map  --(REST)--> GET /jobs/:id/document-map
chunk plan                    |
                              |
drafting calls (streamed) --> StreamObserver --> LiveEmitter (<=4 Hz, coalesced, seq)
OCR pages ------------------>                      |
stage units (exact) ---------------------------> Redis PUBLISH job-events:{id}
                                                   |  (+ SET :live, :progress latest for replay)
                                       ProgressService (pipeline worker, weights, monotonic)
                                                   |
                                       SSE controller: event: progress | live | (stage, narration unchanged)
                                                   |
                                                   v   EventSource listeners (new) + REST map (once)
                                              live store -> cards, outline, %, compare
```

New wire objects (names provisional; schema lives in `shared/schemas/job-live.schema.json`):

| Object | Channel | Rate | Persisted |
|---|---|---|---|
| `DocumentMap` (counts, groups, heading list with word counts, chunk plan, unit names) | REST, built from `job-events:{id}:map` | once per job | Redis, 24 h TTL |
| `progress` `{seq, pct, stage, done, total, unit, estimated}` | SSE event `progress` | at most 1 per second | latest only, `:progress` key |
| `live` `{seq, lane, kind, itemRef, group, title?, excerpt?, cursor?, partial?}` | SSE event `live` | at most 4 per second per job, coalesced | latest per lane, `:live` key, 2 h TTL |
| `compare` `{kind, a:{ref,text}, b:{ref,text}, similarity}` | inside `live` (kind `compare`) | per pair, low volume | no |
| Existing `stage` / `narration` | unchanged | unchanged | unchanged |

Persistence rule: live and progress frames are **not** written to `JobEvent`. The persistence service only handles payloads with a `phase` or `stage`, so new types are skipped naturally (to be pinned by a test).

## 4. Early spikes (week 0, gates the rest of Phase 1)

| Spike | Question | Pass condition | If it fails |
|---|---|---|---|
| A | Does the **deployed** backend (Open WebUI over Ollama or LiteLLM) stream JSON-schema-constrained output incrementally? | Chunks arrive progressively, not as one block at the end | Keep non-streaming; progress steps per call (units still exact); "writing now" shows after each call returns |
| B | Do streamed items come back in **input order**? | Over 20 real chunks, at least 95% in document order | Cursor falls back to "last finished item" with no interpolation |
| C | Does the stream expose the finish reason? | A terminal marker with `finish_reason` can be added to `/llm/chat/stream` | Output-limit detection stays on the non-streaming path only |
| D | Word counts across languages | Hebrew and mixed text within 2% of a reference tokenizer; CJK handled by a character fallback | Use characters / 5 for languages without spaces |
| E | Redis pub/sub headroom | 50 jobs x 4 Hz x 2 KB with 3 subscribers each, no lag | Lower rate, or switch live frames to a stream key |

Output: one short report per spike in `docs/`, then a go / adjust decision before B7 and B8.

### Phase 1 exit criteria

- All existing suites green (ingestion 1,799 passed baseline, orchestrator 1,115, frontend 913).
- Flags off: golden outputs unchanged and no new Redis keys.
- Flags on: events validate against the schema; golden trees identical; no job fails because of an emitter error.
- Spike results recorded and any fallback decisions made.
- Rate and size budgets from Phase 3 met in a first smoke run.

### Rollout

Deploy dark (flags off). Enable on the dev stack first, then staging. Stage 1 enables the map, units and percentage. Stage 2 enables streaming per pass (start with the large drafting pass for Word files).

## 7. Phase 3: stability and performance review

Goal: prove the feature is safe to leave on, with numbers.

### Budgets (proposed, adjust after the first measurements)

| Item | Budget |
|---|---|
| Live frames | at most 4 per second per job; each at most 2 KB |
| Progress frames | at most 1 per second per job |
| Document map REST | at most 300 KB compressed for a 5,000-heading document |
| Redis memory per running job | at most 1 MB |
| Orchestrator event-loop lag, p99 | under 50 ms with 20 concurrent jobs and 3 viewers each |
| Streaming overhead on a drafting call vs non-streaming | under 3% in total call time |
| Ingestion CPU for the observer | under 2% of a worker for a 150-item chunk |
| Browser main-thread cost of live updates | under 5% over baseline on a 5,000-heading document, no long task over 50 ms |
| Percentage | never decreases; moves at least once every 30 s while a streamed call is active; final step under 5 points |

### Work packages

| ID | Review | Method |
|---|---|---|
| S1 | Load and soak | Mock-LLM harness emitting streams at realistic speeds; N concurrent jobs x M viewers; measure Redis operations and memory, orchestrator CPU and loop lag, SSE write queues, ingestion threads, browser profiler traces. Run 2 hours for leaks (subscribers, intervals, Redis keys) |
| S2 | Streaming stability | Failure injection list from Phase 1 plus: backend without structured streaming (automatic per-model fallback, remembered), cancellation closes the stream, duplicated items after retry, one extremely long item, very large chunk |
| S3 | Concurrency | `survey_chunk_concurrency` and `survey_branch_concurrency` above 1: lanes, `seq` monotonic, latest snapshots consistent, no leakage between jobs (key namespace tests) |
| S4 | Security and privacy | Owner scoping on SSE and REST, excerpt and text caps, no persistence or logging of document text, key TTLs, shared Redis exposure, output encoding (excerpts and LCS rendered as text), classification (Company/Internal) confirmed with no external service in the path |
| S5 | Failure and rollback drills | Flag off mid-run; Redis down (best effort, never fails a job); orchestrator and ingestion restarts mid-run (replay restores the screen); watchdog behavior unchanged |
| S6 | Calibration | At least 10 real runs across the four types. Compare the counted percentage with the true elapsed fraction; tune stage weights (feed the same duration history `eta.service.ts` already fits); record the error. Acceptance: monotonic, no visible stall, final jump small |
| S7 | Accessibility and usability pass | Screen reader smoke on the running screen; keyboard path; phone; one moderated session with a real user watching a real job |
| S8 | Documentation | Revise `job-transparency-design.md` (counts and streaming first, tokens secondary); `runbook.md` (flags, kill switches, metrics); `architecture.md` (event and REST contracts); an ADR for streaming the drafting calls; `DESIGN.md` amendments merged |

### Go / no-go checklist

- Budgets met in S1 with margin; no leak over 2 hours.
- S2 and S5 drills pass with no job failing because of the feature.
- S4 review signed off.
- S6 error within the agreed band; otherwise ship the percentage with the "estimated" label.
- Rollback rehearsed: each flag off returns today's behavior, verified by the golden comparison.

### Rollout and monitoring

Dev, then staging, then production behind flags, one capability at a time (map and percentage, then streaming per pass). Watch: emitter errors, Redis memory, SSE connections, streaming fallback rate, percentage regressions (should be zero), and the stale-job watchdog count.

## 8. Risks

| ID | Risk | Mitigation |
|---|---|---|
| R1 | "Reading now" is inferred, and output order may not match input order | Spike B; copy says "Working on"; cursor interpolation only when order holds; otherwise "last finished item" |
| R2 | The backend does not stream structured output well (Open WebUI, Ollama, LiteLLM differ) | Spike A; automatic fallback per model; non-streaming path untouched |
| R3 | Streaming changes retry and failure behavior | Final parse stays the source of truth; fallback before first byte; `reset` frame after; failure-injection suite |
| R4 | Event volume overloads Redis, SSE or the browser | Throttle and coalesce at the source; latest-only keys; backpressure; budgets and S1 |
| R5 | Document text exposure | Caps, owner scoping, TTL, no persistence or logs; S4 review |
| R6 | Percentage looks wrong or stalls | Exact units, monotonic clamp, stage with no unit moves in whole passes; S6 calibration; "estimated" label fallback |
| R7 | The UI regresses today's screen | Flags, fallbacks, compatibility matrix, existing suites untouched, Playwright baselines |
| R8 | Concurrency (chunks and branches above 1) breaks ordering | Lanes, `seq`, S3 |
| R9 | Large documents (thousands of headings) | Map cap and summaries, virtualized outline, REST size budget |
| R10 | Scope creep toward a log or run controls | Out of scope list; the live view is an index of the current work, not a history |
