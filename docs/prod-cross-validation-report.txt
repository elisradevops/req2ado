## 1. Original Requirement (verbatim restatement, source: `docs/architecture.md`)

### 1.1 Problem

Customer requirements arrive as heterogeneous documents (signed contracts, informal surveys, deeply-nested engineering ICDs) in mixed formats (txt/md/docx/pdf/scanned-pdf/xlsx, with tables and figures). They were hand-entered into on-prem Azure DevOps / TFS as work items — slow, error-prone, non-traceable.

### 1.2 Required outcome

A platform that automates conversion of these documents into a hierarchical work-item tree (Epic → Feature → Requirement, with sub-levels) with full traceability (Customer ID + source reference + fidelity hash), in **two operating modes**:

- **BASELINE** (contract-signed): strict, verbatim, provably faithful (hash-verifiable), LLM disabled by default, deterministic.
- **SURVEY** (informal): generative — distills formal "shall"-style requirements with taxonomy tags from informal narrative text.

### 1.3 Required product shape

A **full GUI web platform** (matching an existing internal tool's visual language, "DocGen") where a user:
1. Logs in with an Azure DevOps Personal Access Token (PAT).
2. Uploads a document.
3. Picks a mode (BASELINE or SURVEY).
4. Previews the inferred work-item tree before anything is written (a "dry-run").
5. Confirms — the platform writes idempotent, parent/child-linked work items to an on-prem ADO server.

Heavy processing (parsing, OCR, embeddings, LLM calls) must run on a **job queue + worker pool**, not inline in the request/response cycle, for scale. ADO writes must go through a **custom-built MCP server** (not a third-party or previously-existing one), using the MCP HTTP Streamable transport. LLM calls must go **server-side through a redaction proxy** to a configurable LLM endpoint — raw document content must never reach an LLM unredacted. The product must be fully documented in code, with an **in-app wiki/guidelines page plus tooltips/popovers** on non-trivial controls.

### 1.4 Locked architectural decisions (from original planning Q&A)

| Area | Decision |
|---|---|
| Repo | Standalone repo inside the `elisradevops/` workspace (own dependency boundary). |
| Stack | Hybrid: TypeScript (React GUI, Node orchestrator, MCP server) + Python (ingestion/OCR/embeddings service). |
| MCP server | Built fresh, from scratch — explicitly NOT reusing an existing internal MCP server (`elisra-mcp-ado`). Generic ADO REST conventions may be reused as documented knowledge, not as a dependency. |
| MCP transport | HTTP Streamable (networked, multi-client, containerized) — not stdio. |
| ADO target | On-prem TFS/ADO Server, api-version fallback ladder `7.1 → 5.1 → none`, self-signed TLS via CA-trust (never disabling certificate verification). |
| PAT entry | Login screen pattern (matching two existing internal tools' UX). Header-passed, in-memory/session only — never persisted to disk or logged. |
| LLM access | Backend proxy, redact-first. An OpenAI-compatible endpoint reached server-side by config URL; redaction of sensitive content runs before every outbound call. |
| Scale | Job queue + worker pool (Redis + BullMQ for orchestration; the Python ingestion service horizontally scalable as an independent compute tier). |
| Leveling | Auto-detected by mode: deterministic heuristic in BASELINE, LLM-driven in SURVEY. |
| Ingestion formats | All of: txt, md, docx, pdf (text-native and scanned/OCR), xlsx, tables, figures — required in the first phase, not deferred. |
| GUI | Matches the "DocGen" visual language; built with deliberate design-system discipline (not a generic/templated look); MUI + AntD component patterns; a real design-token system. |
| Docs | Full TSDoc/docstring code documentation + an in-app Wiki/Help page (rendering a maintained user guide) + tooltips/popovers on every non-trivial control. |
| Backend framework | NestJS (dependency injection, guards, request validation) — chosen specifically for its scalability/security posture. |
| Database | Postgres + Prisma, storing jobs, an audit trail, an idempotency map, and users/roles. |
| App auth | The ADO PAT is the sole credential for BOTH identity and permissions — there is deliberately no separate application-level role/permission system. Login validates `{orgUrl, pat}` directly against the ADO Server's own identity endpoint; no external Identity Provider is required (Azure AD support may exist in code as an unused future option, since an App Registration is unavailable in this deployment context). Every authenticated user maps to nothing more than their ADO identity — the ADO server's own permission model (whatever that PAT's account is authorized to do in ADO) is the only real access-control gate that should exist. |

Additionally, ADO REST conventions that MUST be correctly implemented (not merely referenced) in the custom MCP server:
- PAT authentication as HTTP Basic auth with an empty username.
- On-prem TLS handled via CA-trust — `rejectUnauthorized: false` (disabling verification) is explicitly disallowed.
- API-version fallback ladder: try `7.1`, then `5.1`, then no explicit version.
- Retry/backoff on HTTP 429 and 5xx responses and on network errors, with exponential backoff and jitter.
- Bounded concurrency, and work-item batch operations chunked at 200 items per batch (ADO's own server-side limit).
- Writes performed as JSON-Patch documents against the correct ADO REST endpoints, with parent/child links created via the correct relation operation, not by any other mechanism.
- Field reference names (including any custom "Customer ID" field) resolved by querying the target ADO project's real field list at runtime — never hardcoded to a guessed name, since real customer ADO projects are not guaranteed to use any particular custom field naming convention.

### 1.5 Required BASELINE-mode behavior

- Strict, verbatim extraction — provably faithful, verifiable via a content hash.
- LLM must be disabled by default for this mode.
- Deterministic: identical input must produce identical output on every run.
- Extracted titles must be ≤256 characters and must be extracted (truncated/derived) from source text, never summarized/generated.
- `TBD`/`OPEN` markers and figure placeholders in source documents must survive extraction, not be silently dropped.

### 1.6 Required SURVEY-mode behavior

- Distills informal narrative text into formal "shall"-style requirement statements.
- Applies taxonomy tags to each generated requirement (functional, non-functional, interface, performance, regulatory, safety, security, operation, maintenance, feature, behavior).
- Each generated requirement must be individually traceable/verifiable back to its source.
- Must be reachable and usable through the actual running product — not merely implemented as disconnected logic.

### 1.7 Required deduplication behavior

- Embedding-based near-duplicate detection at a similarity threshold of ≥0.90.
- Scoped per Area Path (a duplicate in a different Area Path is not a duplicate for this purpose).
- Vector store must be local (e.g. Chroma) — no external cloud dependency, for data-sensitivity reasons.
- Must be reachable through the actual running product, and must correctly prevent duplicate ADO work-item creation for near-duplicate submissions, without corrupting existing ADO data (i.e., it must never silently re-parent or overwrite an existing item based on a probabilistic match).

### 1.8 Required security posture

- PAT never logged anywhere, under any circumstance.
- Every MCP server request requires a bearer credential.
- Secret comparisons must be constant-time (no timing side-channel).
- All external transport must be HTTPS.
- On-prem TLS uses CA-trust, never a disabled-verification shortcut.
- All route input validated against a schema.
- Rate limiting present.
- Upload size and file-type limits enforced.

### 1.9 Required scale & operations behavior

- Multiple concurrent jobs must complete correctly without any shared-state corruption.
- A durable audit trail must be persisted for every job's lifecycle events.
- Job progress should be pushed to the UI (Server-Sent Events), not purely polled.
- A failure partway through an ADO write must be recoverable — not leave a job permanently stuck.

### 1.10 Required repository & deployment shape

- `docker-compose up` must bring up the entire real stack.
- Shared type definitions (`shared/`) must be single-sourced across the TypeScript and Python halves of the codebase, to prevent cross-language type drift.
- A `deploy/` folder with a reverse proxy (nginx) and TLS termination configuration for production deployment.
- A full documentation set: architecture, runbook, API reference, prompt documentation, security documentation, and a user guide.

### 1.11 Data-sensitivity constraint on this delivered build

This delivered codebase is **explicitly an abstracted/genericized implementation** of the above request, for data-sensitivity reasons — no real company/customer specifics (real ADO tenant, real document samples, real field names, real LLM endpoint) exist anywhere in this codebase. It uses a mock ADO backend for development/CI, synthetic test fixtures, and runtime-discovered (never hardcoded) field names. This is a deliberate, correct way to satisfy the underlying requirements in a sanitized codebase — it is not itself a gap, and should not be scored as one. Anywhere this report marks a requirement **Met (abstracted)**, the underlying mechanism is real and correct; what remains is confirming it against your actual production environment (a real ADO tenant, a real LLM endpoint, real documents) — see Section 5 for exactly how to do that.

### 3.4 Deduplication

| # | Requirement | Status | Evidence |
|---|---|---|---|
| 1 | Embedding-based near-duplicate detection, ≥0.90 similarity threshold | Met | `ingestion/app/dedup/check_for_duplicates.py`; threshold behavior tested at both boundaries (0.89 = not a duplicate, 0.91 = duplicate); invoked live via a new `POST /dedup/check` route, called from the orchestrator's `DryRunService.diff()` after an exact-hash lookup misses |
| 2 | Scoped by Area Path | Met | `area_path` is threaded through the entire call chain and proven correct at the HTTP route level — two dedup-check requests differing only by `area_path` do not cross-match each other |
| 3 | Local vector store (Chroma), no external cloud | Met (abstracted) | `ingestion/app/dedup/vector_store.py` `ChromaVectorStore` uses a local, on-disk `PersistentClient` — no external network dependency. **Known, explicitly documented limitation, not fixed in this phase:** this local store does not survive horizontal scaling of the ingestion service — if you run more than one ingestion instance, each holds an independent, incomplete corpus, and dedup correctness degrades. The code comment above the singleton construction in `ingestion/app/main.py` states this explicitly. Closing this requires externalizing Chroma to a shared server (`chromadb.HttpClient` against a real Chroma deployment) — real, separate infrastructure work, out of scope for this phase |
| 4 | Reachable end-to-end through the running product, without corrupting existing ADO data | Met | `orchestrator/src/modules/pipeline/jobs.service.ts` `confirm()` upserts every genuinely-new ADO item into the vector store after creation (best-effort — an upsert failure is logged but does not fail the already-succeeded ADO write). The dry-run diff surfaces a `dedup_skip` action, kept **distinct** from the exact-hash `reuse` action (with its own `similarity` score), rendered in the frontend as a visually distinct marker so a human reviewer can tell a certain match from a probabilistic one |

**Two safety-critical invariants for this capability — verify these specifically, they are correctness properties, not features:**

1. **Fail-open on dedup-service failure.** If the embedding/dedup service is unreachable, the dry-run diff must fall through to `action: 'create'` for that node rather than failing the whole job. Verify in `orchestrator/src/modules/writeback/dry-run.service.ts`: the dedup-check call sits inside a `try/catch`, any thrown error is logged, and the loop falls through to the normal `create` push. This matters because BASELINE-mode jobs had **zero** dependency on the LLM/embedding services before this feature existed — if this fails closed instead of open, an unrelated service outage would newly break BASELINE jobs that used to work reliably. **This was independently verified by a separate adversarial code review pass, not only by the original implementer.**
2. **A probabilistic match must never re-parent a real existing ADO item.** If a node is flagged `dedup_skip` (matched an existing item by embedding similarity, not exact hash), and that node has children of its own in the current submission, those children may correctly link up to the matched real ADO item. But if the `dedup_skip` node itself is a CHILD of something else in the tree, it must NOT be re-parented under a new parent — that would silently mutate real ADO hierarchy based on a similarity guess (≥0.90 is not certainty), which is a real data-integrity risk, not a cosmetic issue. Verify in `jobs.service.ts` `confirm()`: pass 2 (the parent-linking pass) explicitly skips `linkParentChild` whenever `entry.action === 'dedup_skip'`. **This was independently verified by a separate adversarial code review pass, and covered by two dedicated unit tests** (`orchestrator/test/jobs.service.spec.ts`: one proving a `dedup_skip` node's own children link correctly, one proving a `dedup_skip` node acting as a child is never re-linked).

**Not yet verified live:** a golden end-to-end scenario for this exists in `scripts/run-golden-e2e.sh` (submits a near-duplicate of an already-confirmed document and asserts a `dedup_skip` result appears) but has not been executed live in this development environment — see Section 4, item 1.

## 4. Not Yet Verified End-to-End (read this before deciding go/no-go)

These items are either genuinely missing (listed again here for visibility) or **code-complete but not yet exercised against a real environment** — the distinction matters for how you should treat them:

1. **Live execution of the SURVEY and dedup golden end-to-end test scenarios.** Both scenarios exist as real, runnable scripts (`scripts/run-golden-e2e.sh`, scenarios "job #3" and "job #4") that drive the actual services against a real local LLM. In the development environment where this codebase was built, these could not be executed because an unrelated pre-existing process was already occupying the local database port required by the script's own setup step — this is an environmental conflict specific to that one development machine, not a defect in the code or the test itself. **Action required: run `scripts/run-golden-e2e.sh` in a clean environment (or on the production network) and confirm all four scenarios (BASELINE create, BASELINE idempotent re-run, SURVEY, dedup) pass.**
2. **A real write against your actual on-prem ADO tenant.** Every precondition is met in code — the per-request PAT credential flow, real field content, parent/child linking, and CA-trust TLS are all implemented and unit/integration tested — but the literal HTTP round-trip against a real ADO server has never been executed, because the development environment had no such access. **Action required: run the pre-flight check and a full login → upload → confirm cycle described in Section 5.**
3. **Real production LLM endpoint.** SURVEY mode currently reaches a small local model (`llama3.2:1b` via a local Ollama installation) through the redaction proxy, not your real production LLM endpoint. The proxy/redaction wiring is real and correct; only the specific model behind it is a stand-in. **Action required: point the LLM proxy configuration at your real endpoint and re-run the SURVEY golden scenario.**
4. **Real customer document samples.** All ingestion format support was tested against synthetic fixtures, not real customer documents, per this delivery's data-sensitivity constraint. **Action required: run real (or realistically representative) document samples through the ingestion pipeline once available.**
5. **Config-override for Customer ID field resolution.** The runtime field-discovery mechanism works and is tested, but there is no config surface yet for an operator to explicitly specify a Customer ID field name if none of the currently-known candidate names exist in your real ADO project. Only relevant if your real project's custom field doesn't match the candidates already coded.

## 5. Test Plan for Closing the Remaining Verification Gaps

Run these against your real production network, in this order:

1. **ADO connectivity pre-flight.** `curl -u :<real-PAT> "{ADO_BASE_URL}/_apis/connectionData?api-version=7.1"` — confirms the real server is reachable and identifies which api-version it actually supports (relevant to §3.2, item 5).
2. **Real end-to-end write.** Through the actual UI: log in with a real PAT, upload a real (or realistic) document, pick BASELINE mode, review the dry-run diff, confirm, and verify the resulting work items in your real ADO project — correct type, title, description, AreaPath, State, and (if applicable) Customer ID field. Then re-submit the identical document and confirm the second dry-run diff is 100% `reuse` with zero new items created.
3. **Golden end-to-end script.** Run `scripts/run-golden-e2e.sh` end-to-end (ensure nothing else on the target machine is occupying the ports the script needs) and confirm all four scenarios pass, including the SURVEY and dedup scenarios.
4. **SURVEY against your real LLM.** Point the LLM proxy's configured endpoint at your real production LLM, submit an informal document in SURVEY mode, and manually review the generated "shall"-style requirements and tags for quality — this is a judgment call the automated tests cannot make for you, since it depends on your real model's output quality, not just on the wiring being correct.
5. **Dedup with a real near-duplicate.** Submit a genuine near-duplicate of an already-confirmed real document (same meaning, different wording) to the same Area Path and confirm it is flagged `dedup_skip` rather than creating a redundant work item; separately, confirm a document with genuinely different meaning is NOT flagged.
6. **Concurrency at your real expected load.** Re-run (or extend) the concurrency test at your actual expected peak concurrent job count, not just 50.
7. **Decide on the four genuinely-missing items** (session-JWT guard, SSE progress, write-failure recovery, deploy/reverse-proxy) — confirm whether any of these block your specific rollout plan, since none of them are ambiguous or partially done; they are simply not yet built.
